# ADR-0012: Owner-authorized major gameplay and persistence evolution

Date: 2026-11-10
Status: **OWNER APPROVED**; engineering implementation follows release gates

## Context

The owner is currently the only active user of the FootClubSim prototype. The accepted Playable Preview (#488) already completes 240 fixtures and can export a full SHA-256-checked career. The v188 engine is deterministic and replayable, but its design cannot generate its own penalty or own-goal decisions, its provisional table is not a complete RPL decision tree, cold replay is expensive, and the M2 personnel/rules pack is incomplete. Treating v188's current algorithms and IndexedDB shape as permanent invariants would prevent material improvements.

On 2026-11-10 the owner explicitly approved changing the **structure, algorithms, save schemas, calculations and introducing new parameters or other architectural changes**, without requiring further permission simply because the new format is different. The owner subsequently clarified that **existing game saves may be lost during the current single-user development/preview stage**, until the final ROADMAP stages. Preview-career migration and backward compatibility are therefore optional, not release blockers. Record of the decision: [M1 #3](https://github.com/StanleyLl0yd/FootClubSim/issues/3#issuecomment-6764582803), [M2 #4](https://github.com/StanleyLl0yd/FootClubSim/issues/4#issuecomment-6764583491).

## Decision

1. **Rebaseline architecture:** new playable career and match-engine versions may replace v188; new parameters, new event taxonomy, altered referee/carding/penalty/own-goal models, a changed competition rules model, a new IndexedDB database/storage schema or an altered public UI are authorized. Do not maintain feature-parallel research engines forever only to keep the original snapshot shape. The existing accepted preview remains a reference for user experience, not an unchangeable internal implementation.
2. **One authoritative playable engine per new career format:** when the redesigned simulation is actually ready, use one clearly identified default game/source version and a single corresponding save contract. Historical-version dispatch is optional in the single-user preview; a deliberately reset career is acceptable instead of permanent legacy compatibility. Never mislabel an old event as having been generated by a new source.
3. **Preview save compatibility is optional:** until the final ROADMAP/release-hardening stages, development builds may invalidate, reset, replace or clear the prototype's local game careers and saved match history, including v188. No migration, legacy reader, conversion report or export preservation is required for each experimental schema change. Prefer a clear in-app version/reset notice when feasible; loss of preview progress is an explicitly accepted cost. This permission concerns only FootClubSim test-game saves, not repository history, source files or other user data.
4. **Reintroduce durability before release:** the prototype may deliberately reset IndexedDB, abandon old journals or start all careers anew as the architecture evolves. Do not claim that preview saves are durable or backward compatible. Before **final ROADMAP acceptance and any stable release**, establish a frozen versioned save contract, and validate persistence, atomic writes, recovery, export/import, interrupted operations, multi-tab conflict handling and quota/eviction behavior under storage gate #155. Once that release-quality gate applies, data loss is no longer an accepted failure mode.
5. **Source-of-truth and tests:** deterministic seed policy, bounded inputs, physical 11v11 availability, score/timeline conservation, source-replayed results, negative-input testing, exact-head CI and full 240-fixture Chrome/Edge/Safari functional regression remain required for deployed gameplay changes. During development, migration tests and legacy read/restore are optional; test the new active format's roundtrip as appropriate, without inventing stability claims. Full atomicity/recovery/eviction testing becomes a **mandatory final release requirement** under #155. Never use arbitrary research rates as official real-world calibration.
6. **Milestone gates stay distinct:** M1 #3, M2 #4, P3/P5 #29/#31 and Safari/quota/recovery #155 remain OPEN until their actual evidence and acceptance. Two full repository-wide exit audits remain mandatory at each required milestone. This authorization is **not** permission to falsely sign off absent tests, to invent official data, or to release a stable build prematurely.
7. **Development priority:** replace weak architecture decisively without maintaining disposable old save formats. Prioritize playable correctness and speed, real penalty/own-goal/discipline support, realistic goal/event distributions, M2 vetted personnel and competition rules, and full UI regressions. Defer exhaustive storage-hardening work until the final acceptance phase, while keeping #155 visibly OPEN.

## Existing decisions modified

This ADR **supersedes the permanent-v188 and preview-save preservation assumptions** in [ADR-0011](0011-playable-first.md) and legacy ROADMAP wording. The product-first goal, reproducible simulation, protected-main governance, security and future stable-release storage requirements remain effective. The earlier M0 evidence pack remains historically immutable as repository evidence, but local prototype career storage may be reset.

## Verification and rollout

Before deploying an **experimental new default engine**: verify its supported new-career path, deterministic replay, full-season regression, basic save/load behavior and signed protected-main CI/Pages. Existing preview saves may intentionally stop loading. **Before final ROADMAP/stable release**: freeze the persistence contract and complete storage gate #155 with authentic browser lifecycle, download/recovery, quota and eviction evidence; establish a release migration policy for the then-supported formats. The current authorization is not a #155 acceptance or a claim that Safari private/eviction tests passed.
