## D03/D05: in-match tactical commands and deterministic replays

A manager may open an interactive match, inspect current match state and **pause**, resume, change replay speed/fast-forward, request substitutions, alter team shape and parameters, or issue available **individual instructions**. A fully automated match remains a first-class equivalent mode, not a different simplified match generator. No real-time pitch rendering is mandatory; event timeline and accessible match statistics are sufficient initially.

- Treat each accepted user or delegated-staff decision as an authorized, versioned **command with virtual match timestamp, sequence, actor, prior game revision and selected tactic/roster delta**. Apply it once at the next legally permitted boundary, e.g. stoppage for substitutions; preserve the explicit command acceptance/rejection reason and the exact execution time.
- Validate remaining replacements, bench legality, active-lineup counts, player availability, IFAB/RPL substitution windows, red cards, injuries and tactical bounds from the **fully verified competition-specific versioned rules pack**. No universal invented "five substitutions" shortcut in a synthetic M0 validator. Individual instructions must not sneak in an unapproved gameplay engine in M0.
- If match processing is fast-forwarded, input commands must be associated with defined virtual-time checkpoints, **not** nondeterministic wall-clock races. The seed/PRNG continuation, commands, order and emitted events all persist so **identical inputs reproduce identical results**. In-match intervention necessarily changes the subsequent simulation trajectory, not previously committed events.
- The AI manager uses the same command validity, authority and event pipeline as the human manager. Pre-match and in-match responsibility delegation are independently controllable: a named authorized member of staff may perform match changes only for specifically delegated duties, and the player can reclaim control at permitted boundaries.
- A M1 engine may supply pause/checkpoint/command capability as a **contract**, but there is **no authorization to implement M1 before M0 exit and later explicit owner approval**. The current `MATCH_LEDGER_VERSION=1` is report-only for shots/full-time and must **not** be retrofitted with unversioned substitution commands; future in-match schema changes explicitly increment protocol versions.

## D07: currency, exchange-rate and accounting invariants

### Three user-visible currencies

- **RUB** (₽), **USD** ($) and **EUR** (€) are the only approved initial currencies. The player may switch the global display currency without changing the native currency of contractual sums, held cash or historical ledger transactions.
- Base reporting currency for the Russian club league is **RUB** by default. A wage or transfer denominated in EUR/USD retains its **native original currency and amount**. Show the chosen display-currency equivalent automatically with the **rate as-of date, quotation time and source**. Changing the display setting never performs a transfer or revalues historical booked results.
- All money is an **integer number of minor units** (kopeks/cents) in a tagged currency, using overflow-safe bounds. All rates are **validated positive fixed-precision decimal or rational quotients**, never raw binary floating-point for accounting; use exact arithmetic (e.g. `BigInt`) for conversions and auditable deterministic rounding **half away from zero once per final converted amount**. Document rounding adjustments explicitly where bookkeeping totals differ.
- Maintain separate operating cash, committed expenditures, wage ceiling and transfer budget, with auditable multi-currency journal entries. A budget display revaluation is **not** a real currency exchange. A true conversion/payment requires an authorized transaction recording input currency+amount, output currency+amount, the **frozen FX snapshot**, simulated/real date as applicable, fee (if any), accounting delta and committed career revision. All entries must balance under the chosen accounting policy.

### Google daily exchange rates, without pretending that a licensed API exists

- Owner-approved **reference**: exchange rates shown by **Google Finance** for the **current real-world date**, not a synthetic game date or an arbitrary official central-bank rate. The source-reference pages include [USD/RUB](https://www.google.com/finance/quote/USD-RUB) and [EUR/RUB](https://www.google.com/finance/quote/EUR-RUB); they are illustrative verified pages, **not** a documented public currency API. Use the two approved Google quotes within one coherent daily snapshot. EUR/USD and reciprocal directions are derived mathematically from those same underlying quotes and labeled **cross-derived**, rather than mixing potentially asynchronous standalone quote pages.
- An online refresh is requested **at most once when the real-world calendar date changes** (and on an explicit user refresh), conditional on permission, service availability and a supported, rights-approved source interface. Persist **source/provider ID, pair, fixed-decimal quote, original quote timestamp, fetch timestamp, reference calendar date and selected timezone**, and explicit stale/availability status. A "today" label requires a source observation date matching today's date in the chosen display timezone; if Google quotes a previous market day, show the actual earlier date rather than inventing an updated quote.
- **CRITICAL source-rights blocker:** [Google Finance's published disclaimer](https://www.google.com/intl/en/googlefinance/disclaimer/) restricts copying, downloading, storing and commercial reuse of quotes without prior written consent, disclaims accuracy and warns of delays. **No licensed automated Google Finance FX feed or permission is presently established.** Do not implement HTML scraping, undocumented endpoints, unlicensed replication or automated API calls under the fiction that a displayed Google page is an integration license. Exact production exchange-rate acquisition and lawful caching **remain a separate M3 integration/release gate**. A non-Google provider must **not** silently replace the user's required Google reference; changing that requirement needs a fresh owner decision.
- **Offline-first behavior:** the game must launch/play without network. If a lawfully acquired saved snapshot exists, show converted values using the **last known date explicitly labeled stale**; never silently call such a rate "today". If no usable snapshot exists, show original money amounts without inventing any exchange rate and mark conversions unavailable. New actual cross-currency payments/conversions requiring an unavailable or stale quote **do not auto-commit** (require a fresh eligible snapshot or an explicit user-approved alternate offline accounting rule defined later). Existing committed financial history and match simulation must never be retroactively recalculated from newly retrieved real-time rates.
- Error and release tests must cover all six ordered nonidentity pairs, identity conversions, timestamp/date/timezone correctness, quote cross-coherence, min/max money amounts, zero/negative or NaN quotes, under/overflow, deterministic cent rounding, stale/offline states, update failures, provider-unavailable and source permission failures, export/import, gameplay resume and historical invariance.
- No Google exchange value or dependent third-party quotation is imported into the present **synthetic M0 pack**. This ADR approves the **design goal**, not a claim that legal API access, daily automatic updates or FX computation are implemented.

## Explicit milestone gates

M0 continues to require source-licensing assessment, actual applicable browser acceptance, final full two-pass repository audit and CI.

**M3:** actual transaction ledger, three-currency cash/contracts, Google-source lawful FX integration, daily quotes/cache/replay and the corresponding tests. **Do not claim M3 finance is complete without a lawful Google integration or an explicit owner-approved revised source strategy.**
