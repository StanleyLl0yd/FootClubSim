# M2 #155: verifying a downloaded full-career backup without restoring it

**Scope:** this is an *operator-assisted release evidence step*, not proof that Safari downloaded anything automatically. Browser APIs cannot assert that a Safari OS download dialog completed. Use an **isolated normal Safari profile** and a disposable fictional career; never clear a primary profile.

1. Record the tested application's exact commit SHA, origin, macOS and Safari versions. Create a disposable playable career, record club and committed match count, and play at least one match.
2. Expand **«Сохранения и архивы»**, click **«Скачать полную карьеру»**, confirm that the `footclubsim-…-full-career.json` file actually exists in Safari's Downloads (Finder). Do not rely on the in-app "created" message to prove this.
3. Select **«Проверить скачанный полный архив без восстановления»**, choose **that exact Finder file**, and observe the verified fixture count and SHA-256/source-replay message. This operation is read-only: no browser IndexedDB transaction or import is performed. A successful check establishes only that the file selected in the OS picker is a valid full-career archive.
4. Select a deliberately modified **copy** of the downloaded JSON (never edit the only good backup). The read-only verifier must reject it. Confirm that the original career and its committed fixture count remain unchanged.
5. Quit Safari **fully** with Cmd+Q, relaunch the same normal testing profile and origin, restore the existing career, and verify the same club and match count. A tab reload alone does not satisfy this step.
6. After preserving the downloaded backup outside the test profile, clear **only this disposable origin's** site data via Safari settings, re-open the app and use **«Восстановить полную карьеру»** with the exact previously verified OS file. Confirm the same club and played matches. An app-generated Blob, injected `File/DataTransfer`, SafariDriver automation window or programmatically assigned file input does **not** fulfill the Finder download and picker evidence requirement.
7. Repeat the relevant storage and recovery checks in an actual **File → New Private Window**. Record success/denial and the documented ephemeral behavior after closing all private windows. Do not expect persistence after the private session ends.
8. Genuine browser-enforced quota failure and organic eviction are **distinct remaining cases**. The artificial Chrome/Edge DevTools override previously did not reject an oversized IndexedDB write; do not record it as success. Use only an isolated test VM/profile for bounded experiments, and obtain a separate documented owner decision if organic eviction cannot be reproduced.

Evidence per case: `main SHA`, browser/OS versions, origin, disposable profile declaration, precise actions, observed club/revision before and after, result `PASS/FAIL/BLOCKED/NOT_TESTED`, saved screenshot or log reference, date and operator. No private player data, tokens, or user-home paths in attached logs. Store the completed matrix in [#155](https://github.com/StanleyLl0yd/FootClubSim/issues/155).

**Automated CI boundary:** Chrome/Edge full-season tests select a **real browser-downloaded file** through the native file input, while SafariDriver supplies a synthetic File constructed from the captured Blob. Both execute the read-only decoder plus corruption rejection and unchanged-career assertion. This still cannot satisfy actual Safari app quit, Private Browsing, OS-level download, natural quota rejection or eviction. The #155 release gate stays OPEN.
